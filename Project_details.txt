## **AutoPercept3D**

**GitHub repo:** `autopercept3d`
**Python package:** `autopercept3d`
**Tagline:** *A reproducible LiDAR perception and 3D visualization workbench for autonomous-driving scene understanding.*
---

# Concise project description

**AutoPercept3D is an end-to-end autonomous-driving perception workbench that loads LiDAR/camera data, applies classical 3D perception algorithms, generates object proposals, evaluates processing performance, and visualizes results through BEV, 3D, and interactive dashboard views.**

The project is not trying to beat KITTI benchmarks. Its value is that it shows you can design a complete research/engineering pipeline: dataset loading, calibration handling, point-cloud preprocessing, clustering, 3D bounding boxes, profiling, visualization, Dockerization, documentation, and later optional pretrained detection.

---

# Recommended MVP scope

The MVP should be strong but controlled.

## MVP dataset

Use **KITTI 3D Object Detection** first.

KITTI is the best first dataset because it has LiDAR point clouds, camera images, calibration, and 3D object labels in a relatively simple format. The official KITTI 3D object detection benchmark contains 7,481 training images, 7,518 test images, corresponding point clouds, and 80,256 labeled objects. ([CVlibs][1])

Do **not** start with Waymo. Do **not** start with full nuScenes. nuScenes is excellent but larger and more complex: the full dataset includes around 1.4M camera images and 390k LiDAR sweeps, which makes it better as a later extension. ([nuscenes.org][2])

## MVP features

Build this first:

1. KITTI frame loader
2. LiDAR `.bin` point-cloud loading
3. Camera image loading
4. Calibration parsing
5. Label parsing
6. Point-cloud ROI cropping
7. Voxel downsampling
8. Ground-plane removal
9. DBSCAN clustering
10. 3D bounding-box approximation
11. BEV renderer
12. Open3D frame visualizer
13. Streamlit dashboard
14. Runtime metrics per frame
15. CSV report export
16. Dockerfile, Makefile, README, docs
17. Demo GIF/screenshots

This is already enough for a very strong portfolio project.

---

# Recommended advanced scope

After the MVP works, add extensions in this order:

1. **Camera projection**

   * Project LiDAR points and 3D boxes onto image plane.
   * Shows calibration and coordinate-system skill.

2. **Simple multi-frame tracking**

   * Nearest-neighbor association first.
   * Optional Kalman filter later.

3. **Pretrained 3D detector**

   * Integrate OpenPCDet with a pretrained PointPillars or PV-RCNN model.
   * OpenPCDet officially provides demo paths for pretrained models and KITTI/custom point-cloud visualization. ([GitHub][3])

4. **nuScenes mini support**

   * Add a second dataset adapter.
   * Demonstrates scalable dataset abstraction.

5. **Unity viewer**

   * Export processed frames as JSON/PLY/NPZ.
   * Unity loads frame data and visualizes point clouds, boxes, tracks, and labels.

6. **CARLA or Rennteam-style extension**

   * Only after the clean KITTI pipeline exists.

# Recommended tech stack

## Core language

**Python 3.11**

Python is ideal because the LiDAR, ML, visualization, and scientific-computing ecosystem is strongest there.

## Core libraries

Use:

```text
numpy
scipy
opencv-python
open3d
scikit-learn
pandas
matplotlib
plotly
streamlit
pyyaml
typer
rich
pytest
```

Open3D is especially useful for point-cloud preprocessing and visualization. It supports common point-cloud operations such as voxel downsampling, plane segmentation, DBSCAN clustering, and bounding-volume operations. ([open3d.org][4])

Streamlit is the fastest first dashboard path because it is designed for building interactive Python data apps quickly, without spending weeks on frontend engineering. ([Streamlit][5])

Plotly is useful inside Streamlit for interactive 3D scatter plots and BEV/metric visualizations. ([plotly.com][6])

## Why not Unity first?

You know Unity, which is a strength. But Unity-first would slow down the perception pipeline because you would need to solve data exchange, rendering, UI, frame playback, and Python/Unity integration before the perception system is mature.

The best strategy:

**Python/Open3D/Streamlit first → export clean intermediate data → Unity viewer later.**

That gives you both a working engineering pipeline and a strong visual-computing extension.

# Full system architecture

Think of the project as six layers.

```text
Dataset Layer
    ↓
Geometry + Calibration Layer
    ↓
Preprocessing Layer
    ↓
Perception Layer
    ↓
Evaluation + Profiling Layer
    ↓
Visualization + Dashboard Layer
```

## 1. Dataset layer

Responsible for loading data, not processing it.

Main classes:

```text
DatasetLoader
KITTIDataset
FrameData
CalibrationData
LabelData
```

A `FrameData` object should contain:

```text
frame_id
point_cloud
camera_image
calibration
labels
timestamp optional
metadata
```

This abstraction is important because later you can add:

```text
NuScenesDataset
CarlaDataset
RennteamDataset
```

without rewriting the perception pipeline.

---

## 2. Geometry and calibration layer

Responsible for coordinate transforms.

Modules:

```text
geometry/transforms.py
geometry/boxes.py
geometry/projection.py
```

Core concepts to implement:

```text
LiDAR frame
Camera frame
Image plane
Homogeneous coordinates
Rigid transforms
3D bounding-box corners
BEV projection
Point projection into camera image
```

This is one of the most important CV/interview parts of the project.

---

## 3. Preprocessing layer

Responsible for preparing point clouds before perception.

Pipeline:

```text
raw point cloud
    → remove invalid points
    → crop ROI
    → remove ego-vehicle points
    → voxel downsample
    → estimate/remove ground
    → return processed cloud + masks
```

Modules:

```text
preprocessing.py
roi_filter.py
downsampling.py
ground_removal.py
```

Recommended first algorithms:

```text
ROI crop:
    x forward: 0 to 70 m
    y lateral: -40 to 40 m
    z height: -3 to 3 m

Voxel downsampling:
    voxel size: 0.15 m or 0.20 m

Ground removal:
    RANSAC plane segmentation first

Optional:
    grid-based ground removal later
```

---

## 4. Perception layer

Responsible for object proposals.

Start classical, not deep learning.

Pipeline:

```text
non-ground points
    → DBSCAN clustering
    → filter tiny/huge clusters
    → compute oriented or axis-aligned bounding boxes
    → classify as unknown object proposals
```

Modules:

```text
clustering.py
bounding_boxes.py
object_proposals.py
tracking.py
```

Initial cluster filtering:

```text
min_points: 20
max_points: 5000
min_box_height: 0.3 m
max_box_height: 4.0 m
max_box_length: 8.0 m
```

Do not overclaim these as real detections. Call them:

```text
classical object proposals
cluster-based detections
unsupervised LiDAR proposals
```

That is honest and technically strong.

---

## 5. Evaluation and profiling layer

Responsible for metrics and reports.

MVP metrics:

```text
total points per frame
points after ROI crop
points after downsampling
ground points removed
non-ground points remaining
number of clusters
number of boxes
preprocessing time
ground-removal time
clustering time
box-generation time
total frame time
approx FPS
```

Optional label-aware metrics:

```text
3D IoU with KITTI labels
BEV IoU
matched / unmatched ground-truth boxes
false proposals
missed objects
```

Do not make label metrics mandatory in the first MVP. Add them after visual pipeline works.

### B. Open3D viewer

# Key risks and how to avoid them

## Risk 1: Starting too big

Bad path:

```text
KITTI + nuScenes + Waymo + CARLA + Unity + deep learning
````

Good path:

```text
KITTI only → classical pipeline → strong visualization → then extensions
```

## Risk 2: Deep learning installation hell

OpenPCDet and MMDetection3D are powerful, but they can consume weeks because of CUDA, PyTorch, spconv, and version issues.

Avoid this by making deep learning an advanced milestone, not the MVP.

## Risk 3: Weak visual output

For your profile, visualization matters as much as the algorithm.

Every milestone should produce visual artifacts:

```text
BEV image
3D screenshot
dashboard screenshot
before/after comparison
failure case
```

## Risk 4: Overclaiming accuracy

Do not say:

```text
I built a production-ready autonomous-driving detector.
```

Say:

```text
I built a modular LiDAR perception and visualization workbench with classical object proposals and extensible support for pretrained detectors.
```

That is accurate and impressive.

## Risk 5: Messy repository

Avoid notebooks-only development. Use notebooks only for exploration. All real logic goes into `src/autopercept3d`.

# Interview explanation

## What problem did you solve?

“I built a workbench for debugging autonomous-driving LiDAR perception pipelines. Instead of only running an algorithm and getting numbers, the system lets you inspect each frame, see how the point cloud changes after preprocessing, visualize clusters and 3D boxes, and measure processing time per stage.”

## Why is it hard?

“The difficulty is not just clustering points. The hard part is building a clean end-to-end system: loading dataset formats correctly, handling calibration and coordinate systems, filtering noisy 3D data, separating ground from objects, generating usable object proposals, and visualizing everything in a way that makes perception failures understandable.”

## What architecture did you design?

“I separated the project into dataset, geometry, preprocessing, perception, evaluation, and visualization modules. This made the pipeline configurable and allowed me to later add new datasets or detection models without rewriting the whole system.”

## What algorithms did you use?

“For the MVP, I used classical LiDAR processing: ROI filtering, voxel downsampling, RANSAC-based ground-plane removal, DBSCAN clustering, and 3D bounding-box approximation. I also added BEV rendering and runtime profiling. Later, the architecture can support pretrained 3D detectors such as PointPillars through OpenPCDet.”

## What tradeoffs did you make?

“I deliberately avoided training a large detector from scratch. Instead, I focused on a reproducible and inspectable pipeline. This made the project achievable while still demonstrating the core engineering skills needed for perception tooling.”

## What would you improve next?

“I would add LiDAR-camera projection, multi-frame tracking, pretrained detector inference, and a Unity-based 3D viewer. I would also add more rigorous label-based evaluation using BEV and 3D IoU.”
